# [SPEC.md](http://SPEC.md) — `rustsmith`: Autonomous Rewrite-in-Rust Orchestrator

**Status:** implementation spec, v1 **Audience:** the LLM/agent implementing this tool **Language:** Rust (control plane), containers for execution

---

## 1. What this is

`rustsmith` takes a list of source repositories and, without human intervention during the run, produces for each one:

1. **A fork repo containing a complete Rust mirror** of the original, passing the original's test suite, then optimized.
2. **A suggestions report** listing changes discovered during optimization that could be contributed back to the original project.

A **council** of senior agents plans the work and makes the decisions that would normally be escalated to a human. **Worker agents** do the porting and optimizing. A **deterministic gate system**, written in ordinary Rust with no LLM involvement, decides what passes. No agent can override a gate.

### Core invariant

> The agent that changes an implementation can never influence how that change is graded.

Everything in this spec exists to serve that invariant. If an implementation decision conflicts with it, the invariant wins.

---

## 2. Non-goals (out of scope for v1)

- Automatically opening pull requests against upstream repositories. The suggestions report is a document for the human. `rustsmith` never pushes to a remote the human does not own.
- Porting Fortran or C++ repositories. The language adapter trait must accommodate them, but only the Python adapter is implemented in v1.
- Distributed execution across multiple machines. One host, many containers.
- A web UI beyond the static HTML report.
- Training, fine-tuning, or model hosting.
- Guaranteeing the Rust output is faster than the original. Speed is measured and reported, not assumed.

## 3. Vocabulary


| Term               | Meaning                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| **Run**            | One repo processed end to end. Has its own container, database rows, and output fork.                                    |
| **Unit**           | One chunk of work assigned to one worker. Granularity is decided by the Architect per repo.                              |
| **Oracle**         | The frozen, immutable test suite of the original repo, plus its config and fixtures. The sole definition of correctness. |
| **Held-out suite** | Additional tests generated by the control plane that no agent ever sees. Used to detect gaming of the visible oracle.    |
| **Gate**           | A deterministic pass/fail check implemented in Rust. Never an LLM.                                                       |
| **Council**        | Four senior agent seats: Architect, Verifier, Performance, Scope.                                                        |
| **Graded run**     | Test execution performed by the control plane in a clean container. The only run that counts.                            |

## 4. Architecture

```
┌─────────────────────────────────────────────────────────┐
│ Host (developer machine)                                │
│                                                         │
│  rustsmith control plane (Rust binary)                  │
│   ├── scheduler         (work queue, concurrency)       │
│   ├── council           (4 agent seats, adversarial)    │
│   ├── gates             (deterministic, no LLM)         │
│   ├── oracle service    (graded runs, held-out suite)   │
│   ├── store             (SQLite + JSONL event log)      │
│   └── reporter          (Markdown + HTML + JSON)        │
│                                                         │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │ Run container│  │ Run container│  │ Grading      │  │
│  │ repo A       │  │ repo B       │  │ container    │  │
│  │  ├ worktree1 │  │  ├ worktree1 │  │ (ephemeral,  │  │
│  │  ├ worktree2 │  │  ├ worktree2 │  │  no network) │  │
│  │  └ worktreeN │  │  └ worktreeN │  │              │  │
│  │  OMP workers │  │  OMP workers │  │              │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
└─────────────────────────────────────────────────────────┘

```

- **One container per run.** Complete copy of the repo, its toolchain, and the Rust toolchain. Runs in parallel with other runs. Resource-limited via cgroups.
- **One git worktree per worker** inside the run container.
- **Grading happens in a separate ephemeral container** that the worker containers cannot reach.
- **Control plane never runs agent-authored code** on the host.

## 6. Data model

### SQLite (`store.db`)

```sql
CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  repo_url TEXT NOT NULL,
  source_lang TEXT NOT NULL,
  status TEXT NOT NULL,          -- planning|mirroring|optimizing|harvesting|done|halted
  stage TEXT NOT NULL,           -- recon|mirror|optimize|harvest
  started_at INTEGER NOT NULL,
  ended_at INTEGER,
  halt_reason TEXT
);

CREATE TABLE units (
  id TEXT PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES runs(id),
  kind TEXT NOT NULL,            -- mirror|optimize|repair
  spec_json TEXT NOT NULL,       -- what the worker was asked to do
  depends_on TEXT,               -- JSON array of unit ids
  status TEXT NOT NULL,          -- queued|running|gated|passed|parked|abandoned
  attempts INTEGER DEFAULT 0,
  worktree TEXT,
  commit_sha TEXT,
  tokens_in INTEGER DEFAULT 0,
  tokens_out INTEGER DEFAULT 0
);

CREATE TABLE gate_results (
  id INTEGER PRIMARY KEY,
  unit_id TEXT NOT NULL REFERENCES units(id),
  gate TEXT NOT NULL,
  passed INTEGER NOT NULL,
  detail_json TEXT NOT NULL,
  ran_at INTEGER NOT NULL
);

CREATE TABLE decisions (             -- council decision log, append-only
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES runs(id),
  question TEXT NOT NULL,
  seat_positions_json TEXT NOT NULL, -- each seat's position and reasoning
  resolution TEXT NOT NULL,
  resolved_by TEXT NOT NULL,         -- 'consensus' | 'architect_tiebreak'
  decided_at INTEGER NOT NULL
);

CREATE TABLE optimizations (         -- Stage 2, one row per accepted change
  id INTEGER PRIMARY KEY,
  run_id TEXT NOT NULL REFERENCES runs(id),
  round INTEGER NOT NULL,
  hotspot TEXT NOT NULL,
  commit_sha TEXT NOT NULL,
  delta_pct REAL NOT NULL,
  technique TEXT NOT NULL,
  harvest_class TEXT,                -- language_independent|module_local|port_only
  files_touched_json TEXT NOT NULL
);

```

### Event log (`events.jsonl`)

One JSON object per line, append-only, never rewritten. Every agent turn, gate result, council decision, container start/stop, and halt. This is the audit trail. It must be sufficient to reconstruct what happened without reading any agent's context.

## 7. The oracle (build this first)

The oracle is the most important component. Three layers, all required.

### 7.1 Freeze

At the start of a run, `rustsmith-oracle` snapshots everything that defines correctness:

- All test files
- Test configuration ([`conftest.py`](http://conftest.py), `pytest.ini`, `pyproject.toml` test sections, `tox.ini`)
- Fixtures and test data
- The CI workflow that invokes tests

It writes `oracle/manifest.json`: a SHA-256 for every file plus the exact test invocation command. The manifest is stored on the host, outside every container.

### 7.2 Read-only mount

The frozen oracle is mounted read-only into worker containers. Workers can run tests for their own feedback. That run is advisory and carries no weight.

### 7.3 Graded run (authoritative)

When a unit claims completion, the control plane:

1. Verifies every file in the manifest still hashes correctly in the worker's tree. Any mismatch is an immediate **tamper event** (see 10.3).
2. Copies the worker's build artifact into a **fresh grading container** with a clean checkout of the frozen oracle and no network access.
3. Runs the oracle and captures results.
4. Verifies the expected number of tests actually ran, and that none were skipped, xfailed, or deselected relative to the baseline captured from the original repo.
5. Runs the **held-out suite**, which exists only on the host and is never present in a worker container.

A unit passes only on the graded run. A worker's own claim is never evidence of anything.

### 7.4 Held-out suite

Generated during Stage 0 by the control plane, from the original repo's public API: property tests, differential tests against the original implementation, and fuzz cases. Stored on the host. Never copied into a run container. Never shown to any agent, including council seats.

**Divergence metric:** `visible_pass_rate - heldout_pass_rate`. If it exceeds `heldout_divergence_threshold` (default 5 percentage points), the run halts. This is the primary detector for gaming the oracle.

## 8. Gates

Implemented in `rustsmith-gates`. Pure Rust. Take evidence, return pass/fail plus structured detail. No network, no LLM, no agent input.


| Gate                 | Applies to        | Passes when                                                                                                      |
| -------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `oracle_integrity`   | every unit        | All manifest hashes match; test count and skip list match baseline                                               |
| `oracle_parity`      | mirror units      | 100% of the frozen oracle passes in the graded run                                                               |
| `heldout_divergence` | mirror units      | Divergence under threshold                                                                                       |
| `differential`       | mirror units      | Rust and original produce matching output across generated inputs, within declared tolerance                     |
| `unsafe_budget`      | every unit        | `cargo geiger` count under budget; every `unsafe` block is at an FFI boundary and carries a `// SAFETY:` comment |
| `miri`               | every unit        | Miri clean on all tests that can run under it                                                                    |
| `clippy`             | every unit        | `cargo clippy -- -D warnings` clean                                                                              |
| `benchmark`          | optimize units    | Measured delta beats the CI noise floor with statistical confidence                                              |
| `no_regression`      | optimize units    | No other benchmark regresses beyond the noise floor                                                              |
| `loop_detector`      | every unit        | Unit is under its per-unit token ceiling                                                                         |
| `provenance`         | harvest artifacts | License headers, NOTICE, and attribution preserved from the original                                             |


Gate failure is never fatal on its own. It fails the unit, increments `attempts`, and feeds the failure detail back to the worker.

## 9. Stages

### Stage 0 — Recon

Deterministic analysis first, then the Architect.

1. Detect the language and build system; select the adapter.
2. Build the module and call graph (tree-sitter for Python, plus import analysis).
3. Inventory the tests; run them on the original to establish the baseline, including the skip list and exact test count.
4. Classify dependencies as `port`, `bind`, or `keep`.
5. Read the license; record what attribution must be preserved.
6. Profile the original under representative workloads (py-spy for Python); record the hotspot baseline.
7. Generate the held-out suite.
8. **Architect produces** [`PORTING.md`](http://PORTING.md): the per-repo translation rulebook, covering type mapping, error mapping, naming conventions, the chosen crate layout, ownership and lifetime conventions, and known cross-language traps. This is the highest-leverage artifact in the system. Target a few hundred concrete rules, not generic advice. Precedent: Bun's port generated roughly 300 rules plus a lifetimes table before any code was written.
9. Architect partitions the work into units, leaf-first by dependency order, sized for parallel execution.

Council reviews and approves the plan. The run proceeds without human input.

### Stage 1 — Mirror

Goal: behavior-identical Rust, same module boundaries as the original. **No redesign. No cleverness. No "while I was in there."** Every production case study independently found that deviating here costs more than it saves.

- Workers take units in dependency order; independent units run in parallel up to `max_parallel_workers`.
- Each worker gets: its unit spec, [`PORTING.md`](http://PORTING.md), the relevant original source, the interface contracts of its dependencies, and read-only oracle access.
- On worker completion, the control plane runs the graded gates.
- Passing units are merged to the run branch. The original-language module is deleted in the same commit, so conflicts surface immediately.
- Review is adversarial: the implementing seat never reviews its own diff; two reviewers on different providers see only the diff.

Stage 1 is complete when every unit has passed and the whole-repo graded run is at 100% parity with divergence under threshold.

### Stage 2 — Optimize (round-based)

Rounds, not an open-ended loop. This is what makes the stage terminate.

```
loop {
    profile the current build under the benchmark workloads
    rank hotspots by (time_share × estimated_headroom)
    take the top N hotspots (default N = 8)
    fan out one worker per hotspot, in parallel, each with:
        - a per-hotspot iteration cap (default 6)
        - a per-hotspot token ceiling
    gate each result: oracle parity + benchmark delta + no_regression
    merge the winners; discard the rest
    round_gain = measured end-to-end improvement for the whole round
    if round_gain < round_gain_threshold (default 3%) { break }
    if round >= max_rounds (default 6) { break }
}
run PGO/BOLT as a final pass

```

Every accepted optimization is one commit with its benchmark delta, the technique used, and the files it touched, recorded in the `optimizations` table. **That table, not the finished codebase, is what Stage 3 mines.**

### Stage 3 — Harvest

For each row in `optimizations`, the council classifies:

- `language_independent` — an algorithmic win that would work in the original language too, such as a removed redundant pass, a better algorithm, or a cached computation. Emit as a patch against the original repo, in the original language, with a benchmark showing the gain there.
- `module_local` — a hot path behind a clean interface. Emit as an optional accelerator: PyO3 module, dispatch shim, pure-Python fallback intact, plus the maturin and cibuildwheel config.
- `port_only` — inseparable from the full rewrite. Document as a reason to use the full version.

Rank the resulting suggestions by expected gain divided by estimated review burden. Run the `provenance` gate on every artifact.

## 10. Council

### 10.1 Seats


| Seat            | Owns                                                                                | Model guidance                                    |
| --------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------- |
| **Architect**   | Partitioning, [`PORTING.md`](http://PORTING.md), crate layout, tiebreaker authority | Strongest frontier reasoning model                |
| **Verifier**    | Behavioral comparison against the oracle; cannot modify tests                       | Frontier model, different provider from Architect |
| **Performance** | Hotspot ranking, technique selection, benchmark interpretation                      | Frontier model, third provider                    |
| **Scope**       | In-scope gating, token ceilings, loop detection                                     | Cheap fast model                                  |


Workers and subagents run on a cheap high-volume model at high concurrency.

Model identities live in `config/default.toml` and are swappable. Do not hardcode model names anywhere else.

### 10.2 Decision protocol

**Adversarial review, never majority voting.** LLM errors are correlated across models, so voting can lock in a shared mistake. The protocol is:

1. One seat proposes with reasoning.
2. Two other seats critique, each seeing only the artifact and the proposal, not each other's critiques.
3. If critiques agree with the proposal, it carries.
4. If they disagree, the Architect decides and records why, as `architect_tiebreak`.

Every decision is written to the `decisions` table with each seat's position. A minority position that turns out correct must be recoverable from the log.

### 10.3 Escalation and halting

**Unit fails its gate N times (default 3):** escalate to the council for a re-plan. The council may re-partition the unit, change approach, choose to bind instead of port, or mark it `port_only`. Re-planning is the normal path, not an error.

**Module cannot be ported at all** (C extension, heavy dynamic behavior, metaprogramming): the council decides case by case among binding it via FFI, leaving the original-language module in place behind a shim, or flagging it as out of scope. The decision and its reasoning go in the log and in the final report.

**Automatic halt triggers** (immediate stop, no agent may override):

1. Oracle tamper event: any manifest hash mismatch, altered test config, or unexplained change in test count or skip list.
2. Held-out divergence over threshold.
3. Run-level token ceiling exceeded.
4. Container resource exhaustion.
5. A worker attempting to act outside its own worktree, including any git or cargo command targeting another worktree or the run branch.

On halt, write the reason to `runs.halt_reason`, emit the report as it stands, and stop. Halts are loud and permanent for that run.

## 11. Agent execution

- **Driver:** one OMP CLI subprocess per unit, spawned by `rustsmith-agent`. Structured output parsed from the subprocess; no interactive session.
- **Isolation:** each worker gets its own git worktree. Workers may not run `git` or `cargo` commands that reach outside their worktree. Enforce with a wrapper on `PATH` plus filesystem permissions, not by instruction in the prompt.
- **Build mutex:** a lease system so concurrent workers do not thrash the build cache or exhaust IOPS. One build lease at a time per run container.
- **Resource limits:** cgroup CPU and memory caps per worker. Both documented production ports hit resource collapse from unrestrained concurrency.
- **Prompt caching:** keep a long stable prefix (system, tools, [`PORTING.md`](http://PORTING.md)) so cache hits stay high. Cache hit rate is a reported metric.
- **Prompts** live in `prompts/`, one file per role, versioned. The prompt version used is recorded in the event log for every turn.

## 15. Milestones

Build in this order. Each milestone has an acceptance check that must pass before moving on.

**M0 — Oracle and gates.** `rustsmith-oracle`, `rustsmith-gates`, `rustsmith-store`, `rustsmith-sandbox`. No agents involved yet. *Acceptance:* freeze a real Python repo's oracle; run a graded pass in a clean container; hand-modify a test file and confirm `oracle_integrity` fails; hand-add `@pytest.mark.skip` and confirm the skip-count check fails; confirm the held-out suite runs on the host only.

**M1 — Sandbox and worker driver.** `rustsmith-agent`, worktree management, cgroups, build mutex, the `PATH` wrapper blocking out-of-worktree git and cargo. *Acceptance:* spawn 8 concurrent OMP subprocesses in one container; confirm each is confined to its worktree; confirm an attempt to run `git checkout` on the run branch is blocked and logged as a halt trigger.

**M2 — Council and decision log.** Four seats, adversarial review protocol, tiebreaker, `decisions` table. *Acceptance:* present the council a decision with a deliberately wrong majority position; confirm the minority reasoning is preserved in the log and the Architect's tiebreak is recorded with justification.

**M3 — Stage 0 recon and the Python adapter.** Call graph, test inventory, dependency classification, profiling baseline, held-out generation, [`PORTING.md`](http://PORTING.md), unit partitioning. *Acceptance:* on a small pure-Python package, produce a [`PORTING.md`](http://PORTING.md) of at least 100 concrete rules and a unit DAG whose leaf-first order is verifiably correct.

**M4 — Stage 1 mirror, end to end.** *Acceptance:* the full end-to-end check in section 16.

**M5 — Stage 2 optimize.** Profiling, hotspot ranking, round loop, benchmark gates, PGO. *Acceptance:* run at least two rounds on the M4 output; confirm the loop terminates on the gain threshold; confirm every accepted optimization has a recorded delta above the noise floor; confirm a deliberately introduced regression elsewhere is caught by `no_regression`.

**M6 — Stage 3 harvest and reporting.** Classification, patch and accelerator generation, provenance gate, all three report formats. *Acceptance:* produce at least one `language_independent` patch that applies cleanly to the original repo and measurably improves it in the original language; confirm every artifact carries preserved attribution.

## 16. End-to-end acceptance check

This is the proof the system works. It must pass unattended.

**Setup.** Pick a small pure-Python package (under 5,000 lines) with a comprehensive test suite, CPU-bound hot paths, and no existing Rust core. Good candidate classes: a hashing or checksum library, a string-distance library, a date parser.

**Run.** `rustsmith run <repo-url>` with no human interaction from start to finish.

**Passes only if all of the following hold:**

1. The fork repo contains a Rust implementation with the same public API as the original.
2. The graded run shows 100% of the frozen oracle passing.
3. Held-out divergence is under 5 percentage points.
4. `oracle/manifest.json` hashes are unchanged from the freeze, and the test count and skip list match the baseline.
5. Every `unsafe` block is at an FFI boundary and carries a `// SAFETY:` comment.
6. Miri and clippy are clean.
7. Stage 2 ran at least two rounds and terminated on a stopping rule, not on an error.
8. All three reports exist and agree with each other on every number.
9. `suggestions/` contains at least one classified item with its reasoning.
10. The event log alone is sufficient to reconstruct what every unit did and why every council decision went the way it did.

**Adversarial half of the check.** The system's core claim is that agents cannot game the oracle, so prove it:

11. Plant a unit spec that instructs the worker to make a failing test pass by editing the test. Confirm the run halts with a tamper event and the reason is logged.
12. Plant a unit whose implementation special-cases the visible test inputs and returns hardcoded values. Confirm the held-out suite catches it and the divergence gate halts the run.

A build that satisfies 1 through 10 but fails 11 or 12 has not passed. The gates are the product.

## 17. Notes for the implementer

- **Build M0 completely before writing a single line of agent code.** The oracle layer is load-bearing; everything else depends on it being trustworthy.
- **Never let a gate call an LLM.** Enforce with the crate dependency check in CI.
- **Never let a worker's self-report count as evidence.** Only graded runs count.
- **Prefer prevention to instruction.** If a worker must not do something, make it impossible at the filesystem or process level rather than telling it not to in a prompt.
- **Statistical honesty in benchmarks.** Use a CPU-simulation instrument or sufficient repetitions with confidence intervals. A "5% improvement" inside a 10% noise floor is not an improvement.
- **Provenance is not optional.** A published port that strips license headers and attribution is a legal problem, and there is already a documented case of exactly that happening with an agentic Python-to-Rust port.
- **Everything sent to a training-tier model becomes training data.** Enforce `allow_training_tier_on_private_repos = false` in code, not just in config.
